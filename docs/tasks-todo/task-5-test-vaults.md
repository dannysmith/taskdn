# Task 5: Test vaults

Throwaway vaults whose dates are always current, built from committed templates by a small toolkit of scripts. They replace `demo-vault/` and `dummy-demo-vault/`, give agents and dev builds something safe to point at (task 6), and become eval fixtures later (tasks 9 and 14). The same toolkit is what Claude uses to build persona vaults.

## Background

- `demo-vault/` is good content: 168 files that read like one freelancer's life (a client with projects, a half-marathon, a Japan trip, a party), with people links, checklists and notes in the bodies.
- Its dates are frozen in 2024–25, and worse, it barely uses date fields. Only 6 of 141 tasks have `due`, 1 has `scheduled` and 4 have `defer-until`, all in 2027, so Today, overdue and newly-available stay empty whatever its dates are shifted to.
- Other gaps: all 9 areas are `active`, one project has the invalid status `dropped`, titles in prose carry years ("Write 2024 year in review"), and bodies mention weekdays and month names ("Tuesday: 5K easy", "birthday is April 5th").
- 111 of 168 files have a filename that isn't the slug of their title (`book-dentist.md` is "Book dentist appointment"). That's useful for link-resolution testing. Frontmatter links all use quoted titles; the plugin test document links by filename.
- `scripts/reset-dummy-vault.sh` copies it to the gitignored `dummy-demo-vault/` and symlinks `~/dev/obsidian-taskdn` into `.obsidian/plugins/obsidian-taskdn`. The plugin's manifest id is `taskdn`, and the vault has no `community-plugins.json`, so the plugin has to be enabled by hand after every reset.
- Debug builds of the desktop app already offer the dummy vault: `get_dummy_vault_paths` in `tdn-desktop/src-tauri/src/commands/config.rs` points at `<checkout>/dummy-demo-vault`.
- `scripts/import-demo-vault-to-things.ts` loads the demo vault into Things, so the desktop app can be compared with Things on similar data (screenshots, interactions). It's for development reference only, and is kept.
- Out of scope: the CLI's and desktop's own test fixtures (deliberately small and separate), and `dannysmith/tdn-obsidian-starter-vault` (a starter vault for users).
- Issue #26 asks for persona vaults generated by Claude.

## Design

### Layout

| Path                     | Committed | Contents                                                       |
| ------------------------ | --------- | -------------------------------------------------------------- |
| `demo-vault-templates/`  | Yes       | `demo/` and `edge-cases/`: complete vaults, openable in Obsidian |
| `demo-vaults/`           | No        | Rendered and generated vaults, used for testing                |
| `scripts/vaults/`        | Yes       | The toolkit: a `bun run vault <command>` CLI over a small library |

A worktree that wants its own vault renders one under its own name (`bun run vault render demo --as demo-my-branch`). Multiple dev apps on separate vaults is a task 6 problem.

### Dates shift, they aren't templated

Each template is a normal, valid vault written as if today were its reference date, which is recorded in a small metadata file at the vault root (`.vault.json`, e.g. `{ "referenceDate": "2026-01-15" }`). Rendering copies the template and shifts every full ISO date (`YYYY-MM-DD`, with or without a time and offset) in frontmatter and bodies by the days between the reference date and the target date (today, or `--date`). The rendered vault's `.vault.json` records the new reference date, so it can be shifted again later.

Because every date moves by the same amount, a consistent template stays consistent: `created-at` before `updated-at`, nothing completed in the future, and so on.

Rules this imposes on template content:

- Dates that should move must be written as ISO dates, in prose too ("Call booked for 2026-01-20").
- No weekdays, month names or years in titles or prose, since those can't move. Partial dates (`2024-06`) and years are left alone.
- Times and offsets are kept as written; only the date part shifts.

### The toolkit

A library under `scripts/vaults/lib/` with one job per module, and a thin CLI over it. Claude uses the same commands when building persona vaults.

| Command                                   | What it does                                                                                       |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `vault new <name>`                        | Empty vault: entity folders, `.obsidian/` base, plugin symlink, `.taskdn.json`, `.vault.json`       |
| `vault render <template> [--as] [--date]` | Copy a template into `demo-vaults/`, shift its dates to the target day, then set it up as `new` does |
| `vault shift <vault> (--to D \| --days N)` | Shift the dates of an existing vault in place                                                      |
| `vault generate <name> [--size] [--seed]` | Build a large vault programmatically, deterministic for a given seed                               |
| `vault report <vault>`                    | Coverage report: counts by status and by date bucket, links, and anything that fails to parse      |
| `vault open <vault>`                      | Print the `obsidian://` link                                                                       |

Library pieces:

- **Setup:** folders, `.obsidian/` base, `.taskdn.json` with absolute paths, plugin symlink. The plugin source defaults to `~/dev/obsidian-taskdn`, can be overridden with an env var, and is skipped with a note if missing.
- **Date shifting:** pure functions over text, so they can be unit tested.
- **Entity writers:** write an area, project or task with valid S1 frontmatter from a plain object. Used by `generate`, and available to persona generation.
- **Report:** parses every entity and buckets it relative to the vault's reference date. Used by the CLI and by tests.

### Obsidian

Every vault, template or rendered, opens in Obsidian with no setup:

- `.obsidian/` with `app.json`, `appearance.json`, `core-plugins.json` (Bases and Templates on, Templates pointed at `templates/`) and `community-plugins.json` enabling `taskdn`.
- The plugin symlinked at `.obsidian/plugins/taskdn`, matching its manifest id.
- `workspace*.json` gitignored in the templates. Rendering keeps an existing `workspace.json`, so Obsidian's layout survives re-renders.

## Gotchas

- **Templates must never be written by a tool.** `tdn`, the desktop app or the plugin would stamp real dates on them and break the reference date. Always work on a rendered copy. Opening a template in Obsidian to read it is fine.
- **Week-based views vary.** Dates shift by days, so what lands in "this week" depends on the weekday you render on. A spread of dates across two weeks either side keeps those views populated.
- **Link style is tied to Spec 1.1.** The demo template links by title, which works in the CLI and desktop but not in Obsidian, which resolves filenames. Task 8 decides how links resolve, so revisit the demo's links then. The edge-case vault covers both styles in the meantime.
- **Obsidian may ask once whether to trust the vault** before it enables the plugin. Check whether that can be avoided, and if not, note it in the README.
- **Rendering over a vault that's open** in Obsidian or the desktop app replaces its files underneath them. That's acceptable; the command prints a reminder.
- **Things import:** the script maps statuses and dates; check it still works against the rendered vault's new date layer.
